# INC-018 — Auto Publisher force-disabled by platform-level safety denial on reservation write

- **Estado:** contained (evidence gathered from a fresh read; reservation not force-completed, no duplicate risk; recurring task remains disabled pending owner/architecture decision)
- **Detectado:** 2026-09-27, via a direct status report relayed by the project owner from the Auto Publisher's own run output
- **Componente / canal / cuenta:** Auto Publisher (ChatGPT scheduled task) → GitHub reservation write step, immediately before the Metricool/Instagram publish call. Account: MATRIX 24 Instagram.
- **content_id:** `matrix24-20260926-virat-kohli-2027-world-cup-final`
- **attempt_id / publish_attempt_id:** none created — the reservation write itself was blocked before any attempt identity was established.

## Síntoma

The Auto Publisher's scheduled run reported:

```
blocked_preflight:github_reservation_write_safety_denial
```

A fresh read of the queue record confirmed: `status: ready_to_publish`, `sha: 65f79ee6527581edfe794143528ec6ee8aa576f8`, no `publish_attempt_id` present, no positive or ambiguous Metricool evidence, a valid 1080×1350 JPEG already generated by Cloudflare, and a 570-character caption plus hashtags ready. Preflight validation of the record itself passed cleanly.

The SHA-conditional GitHub write that reserves the record for this publish attempt (the mechanism that prevents two concurrent publish attempts on the same content) was blocked by a safety layer inside ChatGPT's own execution runtime — not by GitHub, not by this repository's own permissions, and not by any MATRIX 24 validation logic. The runtime treated this single blocked write as non-recoverable within that run and, as a consequence, disabled the entire recurring scheduled task.

## Impacto

- The Kohli story remains stuck in `ready_to_publish`: media is generated and valid, but the record cannot progress because the reservation step that must precede a safe publish attempt never completed.
- No duplicate-publication risk from this specific event: because the reservation write itself was blocked, no `publish_attempt_id` was ever created and Metricool was never invoked. The record is exactly where it was before this run started.
- Broader impact: the Auto Publisher's recurring task was disabled by ChatGPT's platform in response to this one denial, which is the same class of autonomy loss the project owner had already reported informally before this incident (this postmortem is the first run where the exact underlying mechanism was captured directly from the runtime's own output).
- This is external to the repository's own pipeline logic. Every component this project controls — the editorial validator, the Promotion Controller, the Cloudflare Worker, the queue schema — behaved correctly. The failure originates one layer above all of them, inside OpenAI's own task-execution safety controls.

## Causa confirmada y límites

**Confirmed:** ChatGPT's own runtime applies a safety check to the SHA-conditional GitHub write the Auto Publisher performs as its reservation step, and this specific check denied the write. The runtime's own recovery policy treats this denial as non-recoverable inside the run and disables the recurring task rather than retrying or surfacing a soft failure.

**Not confirmed / out of scope for this repository to determine:**
- The exact rule inside OpenAI's safety layer that classified this write as denroyable. Claude has no visibility into ChatGPT's own platform, its safety configuration, or its scheduled-task runtime, and cannot obtain this — this is a hard limit of the current toolset, not an area left uninvestigated.
- Whether this denial is content-specific (something about this particular story, repo, or write payload) or a general policy now applied to any GitHub write of this shape performed by a ChatGPT scheduled task. Recurrence tracking (below) is the only way to tell these apart from this side.

This incident is consistent with, and reinforces, INC-017 (intake editorial write denied by a safety control) and INC-015 (no independent watchdog existed to catch this kind of silent task disablement) — both already in this catalog before this event.

## Reparación aplicada

No code or data repair was needed or attempted: the queue record is intact, unclaimed, and safe exactly as INC-010's "preserve the claim, do not touch on ambiguity" guardrail requires. No blind retry was performed and none is recommended from this side, per this repository's own no-blind-retry invariant — retrying the same write from the same runtime is likely to hit the same safety denial again, and only the project owner (via ChatGPT's own platform) or a redesign of who performs the write can change the outcome.

This postmortem is the repair for the documentation gap: the root cause of the recurring "autonomy loss" reports is now written down with a concrete, reproducible signature (`github_reservation_write_safety_denial`) instead of being inferred from symptoms.

## Guardrails

- The stuck record must not be force-completed, re-reserved, or regenerated by hand outside the existing validated pipelines (per `CLAUDE.md`'s standing prohibition on hand-editing `queue/`).
- No component under this repository's control should assume the reservation write will succeed; the Cloudflare Worker and Promotion Controller already do not depend on it completing on any particular schedule.
- Recommendation for the project owner (architectural, not yet executed — requires owner decision and, for the code portion, Cloudflare deploy access this session does not have): move the SHA-conditional reservation write off the ChatGPT-driven Auto Publisher and onto a deterministic mechanism, mirroring how the Promotion Controller already avoids having an LLM perform a risky conditional write directly. A GitHub Actions step (cron or `workflow_dispatch`, triggered once a record reaches `ready_to_publish`) could perform the same CAS write deterministically, with the Auto Publisher (or a future replacement) only invoking Metricool/Instagram after the reservation is confirmed. This would remove the exact operation that is triggering the platform-level safety denial from ChatGPT's task entirely, rather than trying to make ChatGPT's runtime tolerate it.
- Simply re-enabling the Auto Publisher task without changing what performs the reservation write is likely to reproduce this same denial on the next affected record; this is stated plainly so the owner does not spend a cycle on a fix that only restores the status quo.

## Detección de recurrencia y criterio de cierre

**Detección:** the Health Watchdog scheduled task (`trig_01VFP1aeP57pS6tMucZYUtJj`, every 2h) should surface a stuck `ready_to_publish` record whose age exceeds one Cloudflare cron cycle with no corresponding `publish_attempt_id` — this is exactly the signature this incident produced. Any future report from the Auto Publisher itself containing `safety_denial` in an error code is direct, high-confidence evidence and should be treated as the same class of incident, not a new open question.

**Criterio de cierre:** this incident closes only when one of the following happens, whichever comes first:
1. The Kohli record is safely published (a real Instagram media ID or positive reconciliation, per Production Invariant 6) or safely archived as intentionally not published, by the project owner or a redesigned reservation path; or
2. The reservation write is moved to a deterministic, non-LLM-driven mechanism and observed to complete a full publish cycle without triggering the platform-level denial.

Until then, this incident remains **contained, not resolved**: no ongoing risk to already-published content, but the specific stuck record and the underlying architectural exposure both remain open.
